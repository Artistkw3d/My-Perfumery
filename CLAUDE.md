# CLAUDE.md

## Project Overview
My Perfumery v3 - Flask web application for managing perfume formulations, materials, IFRA compliance, MSDS reports, and a perfumer's notebook with olfactive profiles. Single-file Flask app (`app.py` ~4000 lines) with SQLite database. Rebranded from "Perfume Vault"; legacy seeded company names are auto-corrected on startup. Ships as an offline Windows `.exe` via `launcher.py` + PyInstaller (WebView2 desktop shell).

## Tech Stack
- **Backend:** Python Flask, SQLite3
- **Frontend:** Bootstrap 5 (RTL), Chart.js (polar area charts), Select2, jQuery, Bootstrap Icons
- **Deployment:** Docker (docker-compose), and PyInstaller single-file Windows `.exe` built via GitHub Actions (`.github/workflows/build-windows.yml`) and attached to the rolling `latest` release
- **Templates:** Jinja2 (Arabic RTL interface)

## Key Architecture
- `app.py` contains everything: routes, API endpoints, DB init/migrations, IFRA import, external data fetching
- All templates extend `base.html` (fixed sidebar on desktop, off-canvas on mobile, floating Auto/Desktop/Mobile view-mode toggle persisted in `localStorage`)
- Database auto-creates on first run (`init_db()`); column migrations run via `ALTER TABLE … ADD COLUMN` guarded by pragma checks
- IFRA standards auto-import from `data/ifra_standards.xlsx` on startup (`import_ifra_standards()`)
- External data fetched via urllib (PubChem REST API, TGSC HTML scraping, Scentree API + scraping)

## Database Tables
- `materials` - Raw materials with physical/chemical properties
- `material_msds` - GHS/MSDS data per material
- `material_olfactive` - 14-axis olfactive profile per material
- `formulas` - Formulations with IFRA category selection + `card_settings` JSON + `status` (draft/testing/final)
- `formula_ingredients` - Ingredients with weight, dilution, diluent, `ifra_override` (manual per-row IFRA limit override)
- `formula_drafts` / `formula_draft_ingredients` - Versioned drafts per formula for compare/approve workflow
- `formula_notes` - Notes per formula
- `notebook_entries` - Journal entries (title, category, tags, body, `profile` JSON of the 14 olfactive axes, created_at, updated_at)
- `ifra_standards` - 263 IFRA regulated materials with 18 category limits
- `ifra_cas_lookup` - CAS to IFRA standard mapping
- `families`, `suppliers`, `users`, `company_info`, `production_orders`

## IFRA System
- 18 categories: cat1-cat4, cat5a-cat5d, cat6, cat7a-cat7b, cat8, cat9, cat10a-cat10b, cat11a-cat11b, cat12
- Values: positive float = max %, 0 = prohibited, -1 = no restriction, NULL = not applicable
- Formula ingredients calculation uses category-specific limits from `ifra_standards` table
- **IFRA limit lookup priority** (highest → lowest):
  1. `formula_ingredients.ifra_override` — per-row override, always wins
  2. `materials.manual_ifra_cats[cat_key]` — per-category manual value, edited via the "IFRA يدوي" tab in the materials modal. Stored as a JSON dict on the materials row (e.g. `{"cat4": 2.5, "cat8": 0.1}`).
  3. `materials.ifra_limit` (> 0) — legacy blanket value. The UI input was removed on 2026-04-23; a hidden form field preserves existing values on round-trip but new materials won't get this set.
  4. IFRA standards table by CAS + category
  5. IFRA contributions (constituents of naturals / Schiff bases)
- Use case for the manual layers: IFRA publishes an amendment before the local `ifra_standards.xlsx` is refreshed, or a material isn't in IFRA standards at all.
- Form plumbing: the materials modal has a dedicated **IFRA يدوي** tab next to the read-only **IFRA** tab with a table of 18 per-category inputs (`manual_ifra_cat1` … `manual_ifra_cat12`). Submit collects them into a JSON blob in `materials.manual_ifra_cats`.

## Material composition (mixtures / blends)
- Some materials are themselves blends (a pre-made base, an in-house accord, a commercial captive). They get a **التركيب** tab in the material modal between "IFRA يدوي" and "الملفات" where you list sub-components by picking other materials and assigning each a weight-percent inside the parent. Sum can be < 100% — the remainder is treated as unspecified carrier and not weighted into rollups.
- Stored in a new table `material_composition (id, parent_material_id, component_material_id, pct, note)` with cascade delete on parent removal (also fired in the material delete handler and `delete_all_unused`).
- API: `GET /api/materials/<mid>/composition` returns the rows joined with the component's name/CAS/ifra/ppg; `POST /api/materials/<mid>/composition` with `action=save` accepts `components=<JSON array of {component_id, pct, note}>` and **fully replaces** the list. Self-references are silently dropped; cycles (A → B → A direct or transitive) are rejected with a 400 + Arabic message.
- **Effects in the formula calc** (`api_formula_ingredients`):
  - **Per-row IFRA limit (folds into E3/N3).** When an ingredient is a mixture without its own IFRA source (no manual override, no CAS hit, no annex contribution match), `_resolve_material_ifra_for_cat()` derives a per-category limit from composition: `limit = MIN over components of (component_limit / (component_pct_in_mixture / 100))`. This becomes the row's `ifra_cat_limit` with `ifra_std_type='composition'` and `ifra_std_name="Mix: <binding_component>"`, so the row's L value naturally enters `l_values`/`n_values` and the formula's headline E3/N3 shrinks. Without this, a mixture row would have no per-row limit and the formula could silently violate IFRA.
  - **Unrestricted when derived > 100%.** A derived limit greater than 100% is mathematically meaningless (you can never use more than 100% of a mixture in a formula), so `_derive_mixture_ifra_limits()` and `_resolve_material_ifra_for_cat()` collapse it to IFRA's "-1" (No Restriction) sentinel. UI renders "غير مقيّد" in green; placeholder becomes `→ غير مقيّد`.
  - **Cumulative CAS constraint folded into E3/N3.** Critical for multi-mixture cases — if Iso E Super (or any regulated CAS) appears in three mixtures at different concentrations, each mixture's per-row L might look fine individually, but the cumulative total could still violate the IFRA limit. After `contribution_map` is built and limit-checked, each regulated constituent with `total_pct > 0` contributes a `cumulative_L = ifra_limit / (total_pct / 100)` to `l_values` and `n_values`. Prohibited CAS with any presence appends `0` (forces E3 to 0). Order: per-row loop → contribution_map build → limit check + cumulative-L fold-in → **then** `ifra_final_limit = min(l_values) × 0.99` is computed. This closes the case where the warnings card showed a red cumulative violation while the headline E3 was still green.
  - **IFRA contributions map** — `_expand_mixture_components()` walks the composition tree (capped at 5 levels, cycle-protected) and adds each component's effective formula-% into the same `contribution_map` used by the natural-source contributions, tagged `source_type='mixture'`. Downstream limit checks then enforce IFRA against the merged total (direct usage + naturals + mixture components).
  - **Cost roll-up** — `_effective_ppg()` returns the material's own `price_per_gram` if > 0, otherwise the weighted average of component ppg from composition (recursive). The ingredient `cost` line uses this effective ppg instead of the raw column. Result row carries `effective_ppg` for diagnostic display.
- **Materials modal feedback** — `GET /api/materials?action=get` includes `derived_ifra_limits` (per-cat `{limit, binding_name, binding_cas, prohibited}`) when the material has composition. The IFRA tab renders an extra "محسوب من التركيب" table showing each cat's derived limit + the binding component, and the IFRA يدوي tab uses the same data as ghost placeholders inside each empty input (`→ 4.7 (مشتق)` or `⛔ محظور`) so users see what they'd be overriding.
- UI surface: a small green "خليط" badge appears next to the material name in both the card view and the table view of the materials page when `composition_count > 0`. List endpoint adds `composition_count` per row.

## Duplicate a material (added 2026-08-25)
- User's own framing: "the only difference should be the name" — so this copies everything, not just the core `materials` columns. Button (`bi-files`, labeled "دبلكيت") sits next to edit/delete on both card and table views; `POST /api/materials` `action=duplicate` does the work, `duplicateMaterial()` (materials.html) calls it then opens the new copy's edit modal directly so the user can go tweak whatever should actually differ.
- New name is `<original> (نسخة)` — same suffix convention formulas/notebook entries already use for their own duplicate actions.
- Copies every `materials` column verbatim except `id`/`name` (including `cas_number`, `uses`, `physical_state`/`color`, MSDS-adjacent free-text fields, everything) — **except `photo_file_id`, which is deliberately NOT copied as a raw column value.**
- **Why photo/files get real duplicates, not shared references**: `material_files` rows are scoped to exactly one `material_id`, and the material delete handler wipes files by that column (`DELETE FROM material_files WHERE material_id=?`). Pointing the duplicate's `photo_file_id` at the *original's* file row would leave a dangling reference the moment someone deletes the original — the duplicate's photo would silently 404. So instead, every `material_files` row belonging to the source (photo included, plus any other attachments) gets its bytes read back (`_read_attachment_bytes`, disk-first with BLOB fallback like everywhere else) and re-saved as a brand-new row scoped to the new material via `_save_material_file()` — the same writer normal uploads/photo-fetches use, so there's still exactly one code path that writes attachment bytes to disk. `photo_file_id` on the new material is then repointed at whichever newly-created file id corresponds to the original's photo.
- Also copies `material_msds` (1:1), `material_olfactive` (1:1, scent wheel), and `material_composition` where the source is the *parent* (if the source is itself a mixture, the duplicate is too, with the same component/pct rows) — component-of relationships (rows where the source is someone else's *component*) are correctly NOT copied, since that would silently insert the duplicate into other materials' recipes without being asked.
- Verified end-to-end on the local scratch DB: duplicated a mixture material with MSDS data, a scent-wheel entry, 2 composition components, and a real attached file — every field/table copied correctly, the duplicate's photo served its own independent bytes, and deleting the *original* afterward left the duplicate's photo completely unaffected (confirming the dangling-reference case above doesn't happen). Test material/duplicate/attachment reverted afterward.

## Convert a finished formula into a material (added 2026-08-25)
- User's own framing: a formula, once finished, often becomes a new material in its own right (a base/accord you reuse in later formulas) — but not every formula should, so this is a manual, explicit action (an icon on the formula page), never automatic on save.
- **Button**: `formula.html` header — "تحويل إلى مادة" (`bi-box-seam`) when the formula hasn't been converted yet; once it has, the same slot shows "تحديث المادة" (`bi-arrow-repeat`) + a second "عرض المادة" link straight into `/materials?edit=<id>`. Calls `POST /api/formula/<fid>/convert-to-material`.
- **What it creates**: a normal `materials` row (name defaults to the formula's name, `profile='Heart'`) plus `material_composition` rows — one per formula ingredient, at that ingredient's formula weight-percentage (`weight / total_weight × 100`, the same H quantity `api_formula_ingredients` already computes for the "weight %" column). This is exactly the same shape the composition system already uses for pre-made-base materials, so the new material immediately gets everything that comes with having composition: the "خليط" badge, derived IFRA limits, cost roll-up, IFRA contribution folding — no special-casing needed anywhere else in the app.
- Also seeds the new material's scent wheel (`material_olfactive`) from the formula's own aggregate olfactive profile — the same weighted-by-pure-weight calculation `GET /api/formulas` already does for its card view — so it doesn't land with a blank wheel.
- **Idempotent, not one-shot**: `formulas.converted_material_id` (new nullable column, migrated in `_ensure_db_migrated`) remembers the link. Calling the endpoint again — expected, since a formula usually gets tweaked after the first conversion — re-syncs the *same* material's name/composition/wheel instead of creating a duplicate; `material_composition` rows for that material are fully replaced (delete-then-reinsert) each time, matching how `api_material_composition` already treats a composition save as a full-replace rather than a diff.
- Self-reference guarded: if the formula includes, as an ingredient, the very material it was previously converted into (a formula built partly from its own earlier "frozen" version), that row is skipped when rebuilding composition rather than writing a parent-references-itself row.
- Rejects formulas with no ingredients or zero total weight (400 + Arabic message) rather than creating an empty/meaningless material.
- `materials.html` gained a small companion feature for the "عرض المادة" link to be useful: `?edit=<id>` in the URL auto-opens that material's edit modal once the list has loaded (`maybeOpenFromQueryParam()`), so landing there from the formula page goes straight to the newly created/synced material instead of the bare list.
- Verified end-to-end on the local scratch DB: converted a 2-ingredient formula (30g/70g), got a new material with composition `30%/70%`; changed weights to `50g/70g` and reconverted — same material id, composition updated to `41.67%/58.33%`, no duplicate row created; olfactive wheel came out correctly weighted; converting an ingredient-less formula was rejected with the expected message. Test material/formula reverted afterward.

## Quick-dilute (crystalline / strong-impact materials → pre-diluted form)
- Crystalline raw materials (vanillin, aldehyde C-12, etc.) are usually pre-diluted before bench use. Conceptually a "Vanillin 10% in DPG" is just a 2-component mixture: parent CAS @ 10% + solvent @ 90%. The composition system already handles all the IFRA / cumulative-CAS / cost logic; this feature is the fast on-ramp.
- **Button**: "تخفيف سريع" on the materials page header (next to "إضافة مادة"). Opens a small modal: pick parent material, concentration %, solvent (auto-suggests DPG/IPM/ethanol if present), optional name override. Defaults to 10% concentration.
- **Endpoint**: `POST /api/materials/quick-dilute` with `parent_id`, `concentration` (0 < x < 100), optional `solvent_id`, `name`, `name_ar`, `note`. Creates a new material row inheriting the parent's family / profile / supplier / odor description / olfactive profile, then writes 2 composition rows (`parent @ concentration%`, `solvent @ remainder`). If no solvent picked, only the parent row is written and the remainder is "unspecified carrier" exactly as the composition system already supports.
- **Why this is the right model (not a per-row dilution)**: the diluted form is a stable inventory item that the perfumer weighs out as-is. The formula-row `dilution` field stays at `1` (the material *is* the diluted form). All IFRA derivation flows through composition: derived per-cat limit, "Mix: Vanillin" subtitle on the L cell, cumulative-CAS protection across multiple mixture rows, weighted cost roll-up. Ghost placeholders in the manual-IFRA tab show the derived value before override.
- Auto-generated name format: `{ParentName} {pct}% in {SolventName}` (English) and Arabic equivalent.

## Fix materials that are diluted "by name" only (added 2026-08-27)
- **The bug, found by the user auditing their real library**: some materials predate the Quick-dilute feature (or were entered by hand instead of through it) — their *name* says they're diluted (`"Ambroxan 10% in DPG"`, `"Civettone 1% in DPG"`) but they have no `material_composition` row of their own. Several of these still carry the **same `cas_number` as the pure/undiluted substance** — and in `api_formula_ingredients`, a direct CAS → `ifra_standards` hit takes priority over composition-derived limits, so the IFRA calc silently treated the *entire* weight of, say, "Civettone 1% in DPG" as 100% pure Civettone — a 100x overestimate that could produce a false IFRA violation (or, for materials with no `cas_number` at all instead, the opposite failure: zero IFRA restriction applied when the pure substance they're diluting is actually regulated).
- `_DILUTED_NAME_RE` matches `"<pct>% [in ]<solvent>"` against the exact same diluent vocabulary formula.html's ingredient-row diluent dropdown already uses (`Ethanol, DPG, IPM, TEC, MMB, BB, DEP`) — deliberately narrow so it only fires on a real, known diluent token, never a stray "%" in an unrelated name (e.g. a purity spec).
- `_find_diluted_by_name_candidates(conn)` finds matches among materials that **don't already have composition** (skips ones already properly modeled — verified against the real backup that materials created through Quick-dilute already exist this way and are correctly left alone), then looks for the pure/undiluted sibling two ways: (1) exact case-insensitive name match after stripping the dilution phrase, (2) matching `cas_number` against another material whose name does *not* itself look diluted. If no sibling is found either way, the material is reported as **skipped**, never guessed at.
- `POST /api/materials/fix-diluted-names` does the actual write for everything with a found sibling: adds `material_composition` rows (sibling @ detected%, solvent @ remainder — only if that solvent exists as its own material in the catalog, else the remainder stays "unspecified carrier" per the composition system's existing rule), and **only clears the diluted material's own `cas_number` if it exactly equals the sibling's** — never blindly wipes a CAS that came from a name-only match and actually differs. Button: "إصلاح المواد المخففة بالاسم" on the materials page header, results rendered in the same modal shell the other bulk tools use (fixed list + a "needs manual review" list for anything skipped).
- **No sibling found but the diluted material has its own `cas_number` → auto-creates the pure sibling instead of skipping (added same day, same request).** That `cas_number` *is* the real CAS of the pure substance — the user already typed it in, just on the wrong row (the diluted blend, not a pure component). So rather than leaving it stuck needing hand entry, a new material is inserted (`name=base_name`, that same `cas_number`, family/profile/supplier inherited from the diluted row) and immediately run through `_enrich_material_data()` — the exact same CAS-based pipeline (local reference → PubChem → TGSC → Scentree) every other material uses — so it isn't a bare empty row. Only genuinely un-attributable cases (no name match *and* no `cas_number` at all on the diluted material) still get reported as skipped. Endpoint stays synchronous even with this addition — sibling creation is one more local INSERT plus a single-material enrichment call, not a bulk network job.
- **Verified against the real backup, both passes**: first pass — of ~11 name-diluted materials, 7 (Coumarin, Ambroxan, Labdanum, Civettone, Mimosa, ASTROLIDE-Galaxolide, Castoreum) turned out to already be correctly modeled via composition (created through Quick-dilute previously) and were correctly left untouched; the remaining 4 (Anisyl Acetone, Benzoin Siam Resinoid, Geosmin, Olibanum Absolute) had no separate pure material to reference. Second pass (after adding sibling auto-creation) — all 4 of those got a real pure sibling created (each had its own valid `cas_number` to build from) with genuine enriched data (odor description, flash point, specific gravity pulled from TGSC), correct composition rows, and their own `cas_number` cleared; DPG solvent was found and linked for the 2 DPG-diluted ones, while the 2 TEC-diluted ones correctly got no solvent component since no "TEC" material exists in this catalog (remainder stays unspecified carrier). Re-running the endpoint afterward correctly found nothing left to do (idempotent — no duplicate materials or composition rows on a second click).

## Scale modal print
- The Scale modal (`showScaleModal()` on formula.html) renders a multi-column table of ingredient amounts at user-chosen quantities (1000g/100g/50g/20g/5g by default), in either J% (production) or H% (design) mode.
- A **"طباعة النتائج"** button next to the type/equation line at the top of the results prints the rendered table.
- **Implementation: hidden iframe, not `window.open`.** pywebview/WebView2 (the desktop `.exe` shell) blocks `window.open` as a popup. The print path writes a self-contained HTML doc into an off-screen iframe (`#scalePrintFrame`), then calls `iframe.contentWindow.print()`. Works identically in browsers and in the desktop build, no popup-blocker prompts. The print doc is RTL Arabic, A4, with formula name + calc type (J/H) + today's date as a header above the table. The original `/formula/<id>/print` A4 page is unchanged and unrelated.

## Material file attachments
- Every material has a **الملفات** tab in the modal (right after IFRA يدوي). Users attach PDFs, images, Word/Excel docs, etc. up to 50 MB per request.
- **Storage layout (changed 2026-05-05):** files live on disk under `USER_DIR/attachments/<file_id>.bin`. The DB row in `material_files (id, material_id, filename, mime_type, size, content BLOB, uploaded_at)` now carries metadata only — `content` is `NULL` for new uploads. The BLOB column is kept for two reasons: it's the legacy fallback when restoring a pre-2026-05-05 `.db` backup, and the migration uses it to find rows that still need moving to disk.
- **Migration** runs in `bootstrap()` via `_migrate_attachments_to_disk()`: any row with `content IS NOT NULL` gets its bytes written to disk first, then the BLOB is nulled, then `VACUUM` reclaims pages. Crash-safe (disk before BLOB clear), idempotent, and auto-creates a `pre_attachment_migration` backup the first time it finds work.
- **Upload path** inserts the metadata row first to mint an id, then writes bytes to `_attachment_path(fid)`; if the disk write fails the row is rolled back so we never leak orphan rows pointing at nonexistent files.
- **Read path** (`api_material_file_serve`): tries disk first via `_read_attachment_bytes(fid, blob_fallback)`, falls back to the BLOB only if the disk file is missing. Inline rendering is restricted to `_SAFE_INLINE_MIMES` (image/* except svg, pdf, text/plain); everything else is forced `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff` so user-uploaded HTML/SVG can't XSS as same-origin content.
- **Orphan-keep policy on delete (intentional):** row deletes (single file, material delete, `delete_all_unused`) do **not** unlink the disk file. This preserves restore-from-backup correctness — backups are `.db`-only and don't include attachments, so an older backup that references file ids deleted in the meantime still resolves. Disk usage grows monotonically; an explicit "Clean orphan attachments" action can be added later if it ever matters.
- API: `GET/POST /api/materials/<mid>/files` (list + upload/delete via `action=upload|delete`), `GET /api/materials/<mid>/files/<fid>[?inline=1]` serves the bytes with UTF-8 filename support for Arabic filenames.
- The Files tab is disabled (shows a "احفظ المادة أولاً" hint) until the material has an id — new-material flow must save first to get one. Image files get a 44×44 thumbnail, non-images show a typed Bootstrap-icon glyph.

## Material shelf-life / expiry date (added 2026-08-28)
- The app previously had no concept of a material expiring at all (`lot` existed for batch numbers, but nothing tracked purchase date or shelf life). `materials.expiry_date` (nullable, plain `YYYY-MM-DD` text from an `<input type="date">`) is a deliberately simple, directly user-entered date — not derived from a purchase date + shelf-life duration, since purchase date isn't tracked either and deriving one would need assumptions this app has no basis for.
- Form field sits next to Lot in the Basic Info tab. Included in the material save UPDATE/INSERT (both branches) and flows through `GET /api/materials?action=list|get` automatically since those already `SELECT m.*`.
- `expiryBadgeHtml(m)` (materials.html) shows a badge only when there's something to actually flag — red "منتهية الصلاحية" if `expiry_date` is in the past, orange "تنتهي خلال N يوم" if within 60 days, nothing otherwise (a material with a fine, distant expiry date doesn't need visual noise on every card). Rendered on both card and table views, same spot as the Uses badges.
- No automated alerts/notifications yet (not asked for) — purely visual, checked client-side against `new Date()` whenever the list re-renders.

## Material molecular weight (added 2026-08-28)
- `_lookup_pubchem_physical()` and `_lookup_scentree()` both already returned a `molecular_weight` value from every lookup — nothing ever persisted it, so it silently went nowhere. Found while building the label-printing feature below: the user's own printed label archive always shows a literal `"? g/mol"` placeholder for this field, because it never had anywhere real to come from.
- `materials.molecular_weight` (nullable TEXT) is now a real column, added to `_DATA_FILLABLE_FIELDS` so the normal "تحديث بيانات المواد" bulk pipeline fills it like any other field (same fill-only-if-empty rule). Form field added to the material modal's Physical/Chemical tab, and to all three manual per-material fetch buttons' (`fetchCASData()` etc.) `fillIfEmpty()` calls. TGSC's lookup doesn't return a molecular weight, only PubChem/Scentree do — `fillIfEmpty` already no-ops safely on a missing value, so nothing special needed there.
- Deliberately **not** touched: the older Excel bulk-import path (`/import`) still explicitly excludes `molecular_weight` from what it persists (a long-standing skip-list from before this column existed) — left alone since it's a separate, larger legacy feature with its own hardcoded column mapping, out of scope for this fix.

## Material label / sticker printing (added 2026-08-28)
- New `/labels` page (nav: "ليبلات المواد"), modeled directly on the user's own historical label archive (`Phomemo` thermal-printer label app — a folder of ~150 previously-designed label PNGs/AML files was reviewed to reverse-engineer the exact visual convention rather than inventing a new one). No server-side data needed: `labels_page()` just renders a static shell; materials are searched via the existing `/api/materials/search` (same select2-ajax pattern as the formula ingredient pickers) and fetched via `/api/materials?action=get&id=` once picked.
- **Label design**, faithfully reproducing the archive's most recent/settled style (a May-2025-dated sample was the clearest reference): thick black border; a decorative circle-X mark + the material's single highest-scoring olfactive category in large bold text at the top-left (`topOlfactiveCategory()` — same "pick the winner" logic as materials.html's card-view top-notes chips, just reduced to one instead of the top 4); material name; `CAS N° :<cas>`; and a bottom row with a 3-band pyramid icon (drawn as 3 SVG `<polygon>`s, one filled black per `materials.profile` — Top/Heart/Base maps to top/middle/bottom band) beside molecular weight + flash point, falling back to the archive's own `"? g/mol"` / `"Flash Point : ?°C"` placeholder text when either is unknown rather than inventing different empty-state text.
- **RTL trap avoided deliberately**: the whole app is `<html dir="rtl">` (`base.html`), but label content (English category names, "CAS N°", "g/mol") is always LTR. `.ph-label-inner { direction: ltr; }` is set explicitly — without it, the row holding the icon+category name would silently reverse order under the page's inherited RTL context, putting the icon on the wrong side.
- **Size control**: preset buttons for the two sizes found in the user's own `.aml` templates (50×30mm / "5×3 سم", and 60×38mm / "6×4 سم" — extracted directly from `<labelWidth>`/`<labelHeight>` in their saved Phomemo project XML), plus free-form width/height (mm) inputs. The label's internal layout is fixed at a 50×30mm reference design and scaled via CSS `transform: scale(chosenWidth/50)` rather than re-flowing at every possible size — keeps every element's proportions identical to the reference regardless of the physical size chosen.

Full-resolution image is derived by stripping WordPress's auto thumbnail suffix (`-150x150` etc.) from the returned `<img src>`.
  3. **Fraterworks** — `_fetch_fraterworks_by_name()`, guesses the product handle from the **name** only (fraterworks.com has no CAS-search of any kind, and `robots.txt` disallows `/search` for crawlers — this `/products/<slug>.json` guess is the only automated path allowed). Tried last, only after both CAS sources have already missed. Unmatched materials can still be resolved by the user pasting a Fraterworks product URL by hand (`/api/materials/photo-search/resolve`, unchanged).
  - First hit wins; each source's function returns `None` on no-match/error so the chain moves on silently. `GET /api/materials/photo-search` takes separate `name`/`cas` query params (frontend passes both).
  - **Perfumer's Apprentice (`shop.perfumersapprentice.com`) was dropped entirely 2026-08-22** — user reported its images kept "appearing but not loading/saving." Root cause turned out to be broader than just that one vendor (see hardening note below), but per explicit instruction it was removed from the chain rather than kept as a known-flaky source.
- **Download hardening (2026-08-22):** `_download_and_save_material_photo()` was intermittently hitting 403s on the actual image download step even when the search/match itself succeeded — a real, reproducible issue during testing (stress-tested: 2 of 4 raw direct-image requests to PSH's CDN 403'd without a browser-like request). Root cause: hotlink/bot protection reacting to a non-browser `User-Agent` and/or missing `Referer`, not dead links. Fixed by sending a real Chrome UA string + a same-host `Referer` header, plus one retry after a 1s pause before giving up. Re-verified with a full-catalog stress test after the fix: 4/4 real materials (spanning PSH, Bioland, and Fraterworks as the matched source) saved successfully, 0 failures.
- **Bulk update:** "تحديث صور المواد" button on the materials page toolbar → `POST /api/materials/photo-bulk-update`. Runs the same source chain over every material with `photo_file_id IS NULL` (materials that already have a photo are never touched or re-fetched by this — by design, per explicit user requirement) and reports `{updated, not_found, skipped_no_identifier}`. Runs as a background job (see "Bulk background jobs" below), not synchronously.

## Bulk background jobs (added 2026-08-22)
- **Why:** the first version of bulk photo-update ran synchronously inside the request — the modal showed nothing but a static spinner for however long the whole catalog took, indistinguishable from a frozen tab. Fixed by moving bulk work into a daemon thread with live progress, polled by the frontend.
- **Backend** (`app.py`): `_bulk_job_start(total)` mints a job id and an in-memory status dict (`_BULK_JOBS`, guarded by `_BULK_JOBS_LOCK`); `_bulk_job_update(job_id, **kwargs)` merges fields into it (`processed`, `current`, `status`, `updated`/`updated_count`, `not_found`/`not_found_count`, `skipped_no_identifier`); `GET /api/materials/bulk-job-status?job_id=` reports it. The two bulk `POST` routes (`photo-bulk-update`, `data-bulk-update`) now just query the eligible materials, start a job, launch `threading.Thread(target=..., daemon=True)`, and return `{job_id, total}` immediately — the actual work runs in `_run_photo_bulk_job` / `_run_data_bulk_job`, updating `processed`/`current` after each material so progress is visible mid-flight, not just at the end.
  - Job dicts are in-memory only (not persisted) — they don't survive a process restart, and there's no cleanup/TTL yet (fine at current scale: one job dict per bulk run, an admin-only single-tenant desktop-ish app). If this ever needs multi-worker/gunicorn deployment, `_BULK_JOBS` would need to move to something shared (DB table, redis) since each worker process has its own memory.
- **Frontend** (`materials.html`): `runBulkJob(startUrl, confirmMsg, title, resultRenderer)` is the shared entry point — POSTs to start, then `pollBulkJob(jobId, total, resultRenderer)` fetches `/bulk-job-status` every 1s, rendering a striped/animated Bootstrap progress bar + `"processed / total — current material name"` until `status === 'done'`, then calls `resultRenderer(data)` and `loadMaterials()`. One shared modal (`#photoBulkModal`, title text swapped via `#photoBulkTitle`) serves both bulk actions instead of two near-duplicate modals.

## Material data bulk enrichment (added 2026-08-22, coverage investigated + scoped same week against a real backup)
- "تحديث بيانات المواد" button (next to the photo one) → `POST /api/materials/data-bulk-update`, same background-job mechanics as the photo bulk update.
- **Only ever searches a material once (added 2026-08-27).** `materials.data_searched_at` (nullable timestamp) is set on every material the job touches, regardless of whether anything was actually filled — user feedback: re-clicking the button used to re-hit PubChem/TGSC/Scentree for materials that were already fully resolved *or* already confirmed to have nothing available, which is pure wasted network time for no new data. The bulk query now adds `AND data_searched_at IS NULL`, so a repeat click only processes materials that have never been attempted — genuinely new/never-tried materials (new CAS entered, material just added) still get searched normally, since they start with `data_searched_at` unset. There's deliberately no "force re-check" UI yet — not asked for; if a specific material needs a fresh attempt (e.g. a corrected CAS on one that was already marked), the existing per-material buttons in the edit modal (`fetchCASData()` etc.) still work outside this gate. Note: the very first run after this column was added necessarily searches everything (nothing has a timestamp yet) — that one-time full pass isn't a bug, it only shows the fast-forward behavior from the second run onward.
- **Now also auto-classifies the olfactive wheel (added 2026-08-27).** User-reported gap: this CAS-based path filled every field it targeted except the olfactive wheel ("العائلة العطرية"), which stayed permanently blank unless someone opened the edit modal and clicked "تصنيف تلقائي" by hand — even though the Excel bulk-import path already runs `auto_classify_odor()` automatically when it has a description (`auto_olfactive` flag). `_enrich_material_data()` now does the same: once it has an `odor_description` (freshly filled this pass, or already on the material), and only if the material has **no non-zero wheel score at all yet** (never overwrites an existing profile, even a partial hand-adjusted one), it runs the description through `auto_classify_odor()` and writes to `material_olfactive` via `INSERT OR REPLACE`. Counted in the "filled" total the bulk-job results report.
- **Second gap found immediately after, specific to new materials (fixed same day): `_backfill_olfactive_wheels(conn)`.** The material save handler (`action=='save'`) *always* writes a `material_olfactive` row on every save — including a brand-new material where the user hasn't touched the wheel sliders yet, which inserts an all-**zero** row rather than no row at all. That part was already handled correctly (an all-zero row still counts as "no real wheel data" for the classify check). The actual bug: once `_run_data_bulk_job` marks a material `data_searched_at` (the "only ever searches once" gate above), it's excluded from *every* future bulk-update call — including this wheel classification, since it currently only ran inline as part of the CAS-search loop. A material searched once *before* wheel auto-classification existed (or one whose odor_description got filled some other way) would be permanently stuck with a blank wheel, with no future click ever giving it another chance. Fix: `_backfill_olfactive_wheels()` is a separate sweep — pure local keyword matching, no network calls — that runs **synchronously, unconditionally, on every click** of "تحديث بيانات المواد" regardless of `data_searched_at`, checking every material with an `odor_description` but no wheel data. Runs even when there are zero new materials to CAS-search (`total: 0`) — previously the frontend short-circuited on `total===0` with a generic "nothing to update" message before the backend ever got a chance to do anything else; the response now always carries `wheel_backfilled` and the UI shows it either way. Verified by reproducing the exact failure: a material already marked `data_searched_at` with `odor_description` set but wheel reset to all-zero came back `total: 0, wheel_backfilled: 1` and the wheel was correctly restored — confirming this was really the bug, not a one-off testing artifact.
- **"Uses" tags are a known, expected limitation, not a bug** — they only ever come from the offline reference file's `Uses` column (see the Material "Uses" tags section) plus the Crystal→aura auto-rule; none of PubChem/TGSC/Scentree carry anything resembling a use classification, so a material whose CAS isn't in that one offline reference (or has no Uses value in that row) simply gets nothing added here — same "sometimes doesn't come" pattern as any other field limited by real source coverage, not something this pipeline can fix by trying harder.
- Reuses the exact same three lookup sources as the manual per-material buttons (`fetchCASData()`/`fetchTGSCData()`/`fetchScentreeData()` in the material modal), which were refactored from inline route bodies into standalone functions so they're callable from a background thread without going through Flask's request/session machinery: `_lookup_pubchem_physical(cas)`, `_lookup_tgsc(cas)`, `_lookup_scentree(query)` — each returns `(result_dict, None)` on success or `(None, error_message)` on failure; the original routes (`/api/cas-lookup`, `/api/tgsc-lookup`, `/api/scentree-lookup`) are now thin wrappers that call these and `jsonify` the result, behavior unchanged for existing callers.
- `_enrich_material_data(conn, mid, cas)` runs PubChem → TGSC → Scentree (all by CAS) in that order for one material and writes only columns that are **currently empty** — the same "don't overwrite what's already there" rule the manual buttons use client-side, just enforced against the DB row directly since there's no open edit form in a background job. Allowlisted to `_DATA_FILLABLE_FIELDS` (odor_description, flash_point, specific_gravity, refractive_index, color, appearance, melting_point, boiling_point, ph, solubility, vapor_density, synonyms, vapor_pressure, strength_odor, recommended_smell_pct) — deliberately excludes `ifra_limit` (its manual-entry UI was already removed 2026-04-23 in favor of per-category `manual_ifra_cats`; auto-filling the deprecated blanket field at scale would work against that) and Scentree's profile-inference/uses-in-perfumery text (too fuzzy for unattended writes, stays manual-only via the per-material button).
- **CAS-only by explicit user decision.** The bulk query (`WHERE cas_number IS NOT NULL AND TRIM(cas_number) != ''`) and the per-material skip (`if not cas: skipped_no_identifier += 1`) both exclude materials with no CAS number — that's deliberate, not an oversight: the user manages those by hand and doesn't want a fuzzy name-based match risking a wrong fill. (A Scentree-by-name fallback was built and verified working for this same day, then explicitly reverted per instruction — history in git log around 2026-08-24/25 if it's ever worth revisiting.)
- **Diagnosed against a real production backup (197 materials)** — 9 materials had zero data fields filled despite having a category. Root-caused each by hand:
  - **Real bug, fixed and kept:** `_clean_cas(cas)` — one material's CAS was stored as `"5989-27-5/R"` (an R-enantiomer stereochemistry suffix). None of the three sources recognize the suffixed form at all, so it silently failed everywhere even though the base compound (D-Limonene) is well documented. `_clean_cas()` extracts the bare `\d{2,7}-\d{2}-\d` pattern before any lookup call — recovers the suffixed case, leaves a genuinely wrong value (e.g. an EC/EINECS-format number typed into the CAS field) to fail honestly rather than being coerced into a false match. Applied at every CAS lookup call site, including the single-material `/api/cas-lookup` and `/api/tgsc-lookup` routes, not just the bulk path.
  - **Coverage gap for naturals — since closed, see "Offline materials reference" below.** At the time, the remaining empty materials were mostly natural essential oils (Hinoki wood, Oregano, Yuzu, Star Anise) that PubChem/TGSC/Scentree — all three more compound/synthetic-focused than natural-extract-focused — didn't carry under their CAS number. One material (`"Mandarin Oil, Yellow"`) still needs manual attention: its stored `cas_number` (`"284-521-0"`) is actually an **EC/EINECS number, not a CAS number** — confirmed by independently looking up the material's real CAS (`8008-31-9`) by name on Scentree. `cas_number` isn't a field this feature touches, so this stays flagged for the user to correct by hand.
  - Two more candidate sources were investigated for exactly this natural-oils gap and explicitly **not** integrated: `scentsandflavors.com`'s `robots.txt` lists `User-agent: ClaudeBot` / `Disallow: /` — a deliberate site-owner block on Claude specifically, not routed around regardless of what User-Agent string a request carries. `edenbotanicals.com` has no such restriction, but its search is fully client-rendered (a CAS query and a plain-name query both returned an identical empty result shell over plain HTTP, and no JSON/GraphQL endpoint was discoverable in its bundled JS) — would need real browser network-tab inspection to reverse-engineer, not attempted without that tool available. A general chemical-database search (CAMEO Chemicals, ChemicalBook) also came up empty: both disallow their search/detail paths in `robots.txt`, and ChemicalBook 403s even non-disallowed pages outright.

## Two data-corruption bugs found auditing the real backup (2026-08-25)
Asked to quantify "how many materials actually have data now" — while running the completeness audit (`odor_description` 179/197, `flash_point` 150/197, `specific_gravity` 145/197, `appearance` 171/197, `ph` 5/197, `vapor_density` **0/197**, family_id/category 149/197 — see git history for the full per-field table if needed again), the `vapor_density` zero stood out as implausible and led to two real bugs, one of them serious:
- **Dead code, fixed:** in `_lookup_pubchem_physical`'s experimental-properties section walk, `elif 'density' in h or 'specific gravity' in h:` was checked *before* `elif 'vapor density' in h:` — but "Vapor Density" contains the substring "density", so the broader check always won first. The `vapor_density` branch was unreachable, and worse, a PubChem "Vapor Density" section could silently overwrite `result['specific_gravity']` with the wrong value if it appeared after the real density section in PubChem's data. Fixed by reordering the `elif` chain so `vapor density` and `vapor pressure` are checked before the generic `density` catch-all.
- **Real data corruption on the live catalog, fixed + repairable:** `_lookup_scentree`'s numeric fields (`Density`, `Refractive Index`, `Vapor pressure`, `Molecular Weight`, `Log P`) come through as **comma-decimal** ("0,878", "154,25 g/mol", "1,475 - 1,478") — European formatting, since Scentree is French. `_extract_number()`/`_extract_celsius()` only match `[\d.]+`, so every comma-decimal value silently truncated at the comma: Geraniol's real specific gravity (0.878) was being stored as literally `"0"`. Fixed with a local `_decomma()` helper (`re.sub(r'(\d),(\d)', r'\1.\2', s)`) applied to each numeric field's raw extracted string before parsing — scoped to `_lookup_scentree` only (PubChem/TGSC are US-formatted, no evidence of the same issue there). Verified against the real backup: **47 materials** have a `specific_gravity` or `refractive_index` that's a bare bug-truncated integer (0 or 1) inside the range real values never land on — e.g. "Adoxal (Givaudan)" had `specific_gravity="0"`, `refractive_index="1"` instead of the real `0.852`/`1.450`.
  - The fix alone doesn't retroactively correct already-stored bad values — `_enrich_material_data()` only ever writes to *empty* columns, and these fields are already (wrongly) filled, so the normal "تحديث بيانات المواد" button does nothing for them. Added a **separate one-time repair pass**: "إصلاح بيانات تالفة" button → `POST /api/materials/repair-decimal-data` (same background-job mechanics). `_looks_truncated_decimal(value, lo, hi)` flags a bare-integer value inside a physically-implausible-as-a-whole-number range (`specific_gravity` 0–2, `refractive_index` 1–2 — real fragrance materials essentially never land exactly on a whole number for either), clears *only* that specific column for matching materials, then re-runs `_enrich_material_data()` so the now-fixed extraction refills it. Verified end-to-end on 5 real materials from the backup — all recovered correct decimal values (e.g. Ambroxan `0` → `0.939`).

## Offline materials reference — closes the natural-oils coverage gap (added 2026-08-25)
- User supplied their own reference file (~23k rows, 32 columns — `ID, Names, CasNumber, FemaNumber, NoteClass, IsNatural, NoteTags, Uses, Description` plus ~20 `TGSC *` columns: Name, Notes, CAS/EC/UNII/FEMA/CoE numbers, XlogP3-AA, Molecular Weight, Formula, Category, Appearance, Specific Gravity, Refractive Index, Boiling Point, Acid Value, Odor Type/Strength/Description, Taste Description, Substantivity). Effectively a personal offline mirror of TGSC-style data, largely period-decimal (US-formatted, not the comma-decimal that bit live Scentree above) and — critically — covering many natural essential oils/absolutes the three live sources simply don't have under their CAS number at all.
- **Stored encrypted, not as a plain XLSX** — explicit user request ("لا احد يقرأه" / no one should be able to read it besides the app). `data/materials_reference.enc` is the original XLSX, Fernet-encrypted (`cryptography` package, added to `requirements.txt`). `_MATERIALS_REF_KEY` (the Fernet key) lives in `app.py` right above `import_materials_reference()`, with an explicit comment on the honest security model: this stops the data from being casually opened by anyone browsing the repo or the installed app's files, but the key has to be reachable by the app to import at all, so it's in the same source tree — someone who actually reads `app.py` and runs `Fernet(key).decrypt(...)` could still get the plaintext. That's the ceiling for a distributed desktop app with no server-side gatekeeper; communicated to the user as such rather than oversold. The plain, unencrypted XLSX that was briefly committed before this was scrubbed from the entire git history via `git filter-repo` + a force-push to `origin/main` (explicit user confirmation obtained first, since that rewrites shared history — any existing clone/fork is now incompatible with the rewritten branch).
- `import_materials_reference()` (called from `bootstrap()`, after the IFRA imports) decrypts the `.enc` file into memory (`Fernet(...).decrypt()` → `io.BytesIO`), then parses it the same way `import_ifra_standards()` parses its XLSX — `zipfile` + `xml.etree.ElementTree` over the raw OOXML, no `openpyxl` dependency (matches this project's established no-openpyxl convention, keeping the frozen `.exe` build lean). ~3.3s for the full file on a cold import; idempotent afterward via an `app_meta` key storing the `.enc` file's byte size, so it only re-imports if the file is ever replaced with a different one. Populates `materials_reference (cas_number, name, odor_description, strength_odor, appearance, specific_gravity, refractive_index, boiling_point)`, indexed on `cas_number`. Only rows with a `CasNumber` are kept (~17.2k of the ~23k rows) — rows without one aren't CAS-searchable so they're not useful to this pipeline. If `cryptography` isn't installed, the import is skipped with a log line rather than crashing the app.
- `_lookup_local_reference(conn, cas)` queries this table (some CAS numbers have multiple rows in the source file — merges them, first non-empty value per field wins) and is now the **first** thing `_enrich_material_data()` tries, before PubChem/TGSC/Scentree — it's an indexed local SQLite lookup (effectively instant) vs. multiple live HTTP round-trips, and since these are physical constants that don't change over time, there's no staleness concern trading freshness for speed. Falls through to the live sources for whatever fields it doesn't have, same "fill only empty" merge logic as before.
- Verified against the real backup: of the 9 originally-empty materials, the local reference alone recovers **Hinoki wood, Oregano - Organic EO, and Yuzu distilled eo** (0 fields before → 3-5 fields each) — natural EOs that plain PubChem/TGSC/Scentree lookups could never find under their CAS. Combined with the CAS-cleaning fix earlier, **6 of the original 9** now get real data (D-Limonene, Pharaone, Hinoki wood, Oregano, Yuzu, and Mandarin Oil once its CAS is corrected by hand) — up from 4. The 2 CAS-less materials stay out of scope per the CAS-only policy above; "Star Anise Essential Oil" has a row in the reference file under its CAS but with every field this pipeline reads left blank in that specific row, so it's a genuine source-data gap, not a lookup bug.
- If the user ever wants to swap in an updated copy of their reference file: encrypt the new XLSX with the same `_MATERIALS_REF_KEY` (`Fernet(key).encrypt(open(new_file,'rb').read())`), overwrite `data/materials_reference.enc`, restart — the byte-size check will detect the change and re-import automatically.

## Material "Uses" tags (added 2026-08-25, extended same day)
- `MATERIAL_USE_TAGS` (`app.py`, near `OLFACTIVE_LABELS`) is the built-in source of truth: `{key: {label_ar, label_en, icon}}` for `aroma`, `fixative`, `solvent`, `colourant`, `projection`, `silage`. First four come from the offline reference file's own `Uses` column (col 7), stored there concatenated with no delimiter (e.g. `"aromasolventfixative"`) — `_parse_uses_tags()` does a substring match against the four known keys rather than trying to split on a real separator. `projection`/`silage` are perfumery-craft concepts the user added on top; they don't exist in the source data.
- **`silage` naming correction:** the key is `silage` (unchanged, already the value written into existing `materials.uses` JSON) but its display label/icon were wrong at first — labeled "ذيل عطري" (trail) with a footprint icon 👣, when the user's actual intended concept is *aura* (the scent cloud around the wearer), not a trail left behind. Now `label_ar: 'هالة'`, `label_en: 'Aura'`, `icon: '✨'`. Only the display changed — the stored key stays `silage` so no data migration was needed.
- **Auto-rule:** any material with `physical_state == 'Crystal'` automatically gets the aura tag (`silage` key) — applied once at migration time for existing rows (`_ensure_db_migrated`), re-applied on every manual save regardless of checkbox state (`api_materials()` POST `action=='save'`), **and** re-applied inside `_enrich_material_data()` when `physical_state` gets derived to `Crystal` during a data-refresh run (see next section) — that third path exists because the crystal→aura rule used to only fire through the manual-save form handler, so a material whose `Crystal` state came from an automated enrichment pass instead of a human checking a box would silently miss the tag.
- **User-extensible beyond the 6 builtins:** `custom_use_tags` table (`id, label_ar, label_en, icon`) holds tags the user adds themselves via the "+" control in the material form's Uses section (materials.html → `addCustomUseTag()` → `POST /api/use-tags` action=`add`). Each gets stored/used as `custom_<id>` (e.g. `custom_2`), functionally identical to a builtin key everywhere `uses` is read/written. `_get_all_use_tags(conn)` merges `MATERIAL_USE_TAGS` with these DB rows into one dict; both the `materials` and `formula_detail` routes now call it fresh per request (instead of passing the static `MATERIAL_USE_TAGS` dict) so a newly-added custom tag shows up immediately on both pages without a restart.
- **Edit and delete for custom tags (added 2026-08-27).** `/api/use-tags` gained `action=edit` and `action=delete`, both guarded to only ever touch `custom_*` keys — the 6 builtins are Python constants, not DB rows, so there's nothing for those actions to operate on regardless of what key is passed. `editCustomUseTag(key)`/`deleteCustomUseTag(key)` (materials.html, next to `addCustomUseTag()`) show `prompt()`/`confirm()` (matching this app's existing dialog style for the other bulk-action confirmations), then patch the DOM in place — `useTagCheckboxHtml()` is the one shared markup builder used both for JS-appending a new tag and JS-replacing an edited one, so they never drift from what Jinja rendered on page load. **Deleting a tag also strips that key out of every material's own `uses` JSON array** (`WHERE uses LIKE '%<key>%'` then a real JSON parse/filter/rewrite per match, not a blind string replace) — otherwise a deleted tag's key would linger forever in old materials' data and silently reappear if a future custom tag ever reused the same `id`.
- Edit/delete UI controls only render for `custom_*` keys, both server-side (Jinja `{% if key.startswith('custom_') %}` around the pencil/× icons — written without literal `{% %}` inside the matching JS-side comment, which is a real trap: Jinja parses tag delimiters anywhere in the raw template text, including inside `<script>` comments, so a comment that quotes Jinja syntax verbatim can silently open an unclosed block and break the whole page).
- Storage: `materials.uses` (JSON array, e.g. `["aroma","silage"]` — note the array still uses the `silage` key even though it now displays as "Aura") and `materials_reference.uses_tags` (comma-joined) — both added as one-time `ALTER TABLE` migrations. `_lookup_local_reference()` returns `uses_tags` as part of its result dict, and `_enrich_material_data()` union-merges it into the material's existing `uses` (not fill-only-empty like the other enrichment fields — a material can validly be both `fixative` and `solvent`, and manually-added tags like `projection` or a custom tag should never be clobbered by a data refresh).
- Surfaced in the API as a parsed list (`json.loads`, never the raw JSON string) in three places: `GET /api/materials?action=list`, `GET /api/materials?action=get`, and `GET /api/formula/<fid>/ingredients` (added `m.uses` to the ingredients SELECT, parsed once per row into `temp_results`, then included in the final per-ingredient `result` dict — this is what lets formula.html show a material's tags without a second round-trip).
- Rendering: Python passes the merged `_get_all_use_tags(conn)` result into both `materials.html` and `formula.html` as `material_use_tags`, and each template re-exposes it as a JS constant (`const MATERIAL_USE_TAGS = {{ material_use_tags | tojson }}`) so the icon/label mapping is defined once server-side, with no duplicated JS literal to keep in sync — `addCustomUseTag()` (materials.html) patches the client-side copy of that object in place after a successful add, so the newly-added tag's badge/checkbox work without a page reload.

## Appearance-derived physical_state/color (added 2026-08-25)
- `physical_state` was never in `_DATA_FILLABLE_FIELDS` — none of PubChem/TGSC/Scentree/the offline reference expose it as its own field, so it stayed permanently empty on every enriched material unless the user typed it in by hand (user noticed and asked why, correctly pointing out that `Appearance` — which *is* enriched — almost always implies it, e.g. "White crystalline powder" or "Colorless oily liquid").
- `_derive_state_color_from_appearance(appearance)` (`app.py`, next to `_extract_number`/`_extract_celsius`) does an ordered keyword match against the Appearance text for both physical state (`crystal`→Crystal, `powder`→Powder, `paste`→Paste, `wax`→Waxy, `solid`→Solid, `liquid`/`oil`→Liquid — more specific phrases like `crystal` checked before the generic `solid`) and color (`pale yellow`/`light yellow`/`dark brown`/`light brown` checked before their bare color word, plus colorless/colourless/clear/white/yellow/amber/golden/brown/red/orange/green/blue/black/pink).

## Materials page performance (fixed 2026-08-22)
User-reported "gets heavier the more you browse" — traced to a real Chart.js memory leak, not just catalog size:
- **The leak:** `renderCards()`/`renderTable()` fully replace the list's HTML (`container.innerHTML = ...`) on every `loadMaterials()` call — which fires after nearly every material CRUD action — then create a fresh `Chart.js` polar-wheel instance per visible material card/row via `createPolarChart()`. The previous batch of canvases was never `.destroy()`'d before being thrown away with the old DOM, so Chart.js kept their resize listeners/animation loops alive indefinitely — pure accumulation, worse the longer a session runs (matches "gradually got heavy", not "always was heavy"). Fixed: `createPolarChart()` now returns the `Chart` instance; `renderCards()`/`renderTable()` push each into a shared `miniCharts` array and `.destroy()` the previous batch before rebuilding.
- **Secondary fixes:** material thumbnail `<img>` tags now carry `loading="lazy"` (skips decoding photos scrolled out of view); `GET /api/materials/<mid>/files/<fid>` now sends `Cache-Control: private, max-age=604800, immutable` — a given file id's bytes never change in place (re-fetching a photo mints a new id, per the orphan-keep policy above), so the browser can skip re-requesting the same photo on every list re-render instead of round-tripping to SQLite each time.
- Not yet addressed (flag if it resurfaces): no pagination on the materials list — `renderCards()`/`renderTable()` are still O(n) full rebuilds on every load, and `filterMaterials()`'s advanced-filter pass runs client-side over the full in-memory `materials` array. Fine at current catalog sizes; would need real pagination or virtualization if a catalog grows into the many hundreds.

## App-wide performance — vendored assets, cached migrations, AJAX material search (fixed 2026-08-22)
Follow-up after the materials-page fix above — the user still felt the app was slow after that, so this round measured rather than guessed (timed CDN latency, timed real request round-trips) before touching anything.
- **All CDN dependencies removed.** `base.html`, `login.html`, `formula.html`'s print-iframe, `formula_print.html`, and `contributions_test.html` used to pull Bootstrap, Bootstrap Icons, select2 (+ its Bootstrap-5 theme), Chart.js, jQuery, and Google Fonts' Tajawal from `cdn.jsdelivr.net` / `code.jquery.com` / `fonts.googleapis.com` on **every page navigation** (this is a classic multi-page app — every route is a full reload, not an SPA). Measured cold latency per file: 0.65–0.87s each. For an app that's explicitly shipped as an "offline Windows .exe" (see top of this file), depending on 3 external hosts for every page load was the biggest single issue found. Fixed by vendoring everything into `static/vendor/` (`bootstrap/`, `bootstrap-icons/` incl. its woff/woff2, `select2/`, `jquery/`, `chartjs/`, `fonts/tajawal/` incl. all 12 weight×subset woff2 files self-hosted with a local `tajawal.css`) and pointing every template at `{{ url_for('static', filename='vendor/...') }}` (or a literal `/static/vendor/...` path inside the one place a URL is built in a JS template string, `formula.html`'s print-iframe). `static/` already had a `static_folder` wired up in `app.py` and an empty placeholder file — this was clearly planned and never finished. Also deleted one genuinely redundant duplicate Tajawal `<link>` in `formulas.html` (same font already loaded once via `base.html`, since `formulas.html extends base.html`). Verified via the browser network panel: zero requests to any host besides `127.0.0.1:8000` (and the user's own unrelated extensions) on login/materials/formula/print pages.
- **`get_db()`'s migration checks now run once per process, not once per request.** It's called at ~40 sites across the app, and used to re-run 2× `CREATE TABLE IF NOT EXISTS` + 2× `PRAGMA table_info` + conditional `ALTER TABLE` on every single call. Refactored the body into `_ensure_db_migrated(conn)`, gated behind a module-level `_db_migrated` flag now checked in `get_db()`. **Correctness guard:** `restore_backup()` replaces the live `.db` file with a backup on disk while the same process keeps running — an old backup could be missing columns/tables added since it was taken, so `restore_backup()` explicitly resets `_db_migrated = False` after the file swap, forcing the next `get_db()` call to re-check the freshly-restored file's schema before anything else touches it. (This is the one place besides normal startup where the DB file changes out from under a running process — audited to confirm no other code path does a bulk file replace.)
- **Formula-page material pickers switched to live search instead of baking the whole catalog into the page.** `/formula/<id>` used to server-render a Jinja `{% for m in materials %}` loop into two `<select>`s (add-ingredient, swap-ingredient) — every material in the catalog became an `<option>` in the page HTML on every load, and select2 had to index all of them client-side. Added `GET /api/materials/search?q=` (name/name_ar/cas_number `LIKE`, capped at 30 results, select2's `{results:[{id,text}]}` shape) and switched both selects to select2's `ajax` mode (shared `materialSelect2Opts` config, 200ms debounce). The route no longer queries or passes the full materials list to the template at all. Scales with search results now, not catalog size — matters once a catalog grows past the current dev-scale handful of materials.
- Auto-guess field mapping was expanded on 2026-04-23 to cover all 31 system fields — previously many columns (Synonyms, Lot, Strength Odor, Vapor Pressure, Effect, خصائص, In Stock, سعر القرام/الجرام) fell through to "تجاهل" because their headers weren't recognised.
- New system field `price_per_gram` (سعر الجرام (القرام)) is importable directly. If the user maps a "price per gram" column, it's used verbatim; otherwise `ppg = purchase_price / purchase_quantity` as before.
- Bulk reset endpoint (`action=reset_ifra` on `POST /api/formula/<fid>/ingredients`) clears all overrides for a formula
- IFRA certificate (`/api/ifra-certificate/<fid>`): per-category computed limit is capped at 100% (anything higher becomes "No Restriction"); Composition table lists only IFRA-regulated materials (CAS hit in `ifra_standards` or manual `ifra_limit > 0`)
- MSDS report (`/api/msds/<fid>`): Section 3 lists only ingredients with GHS data (H/P codes, pictograms, or signal word); percentages remain computed from the full formula

## Auth + session secret
- **Password storage (added 2026-05-05):** `users.password` is hashed with `werkzeug.security.generate_password_hash` (default scrypt). Migration `_migrate_plaintext_passwords()` runs in `bootstrap()` and detects plaintext rows by negation against the hash-prefix oracle (`scrypt:` / `pbkdf2:` / `argon2`). First run that finds plaintext auto-creates a `pre_hash_migration` backup, then rewrites every plaintext row in place. Idempotent. Login still works with the same plaintext password the user remembers — `check_password_hash` validates it against the new hash.
- **Login fallback:** if a stored value somehow still looks plaintext at login time (e.g. migration was skipped), the route does a `hmac.compare_digest` and, on success, hashes the password before completing login. So plaintext can never persist past one successful login.
- **Restore safety:** `restore_backup()` already preserves the live admin row across a restore, so even restoring an old plaintext-era backup keeps your hashed credentials at `id=1`. The migration on next startup will hash any *other* user rows pulled in from the restored backup.
- **Per-install random `secret_key` (added 2026-05-05):** `_load_or_create_secret_key()` reads/creates `USER_DIR/secret.key` (64 random bytes). Replaces the previous hardcoded `'perfume_vault_2024_v3'` literal — sessions are now uniquely scoped per install. The file is in `.gitignore`. If the file can't be written, falls back to an in-memory key (sessions still work for the running process).

## Backups
- Live `.db` is at `USER_DIR/database/perfume.db`; backups under `USER_DIR/database/backups/` named `backup_<YYYYMMDD>_<HHMMSS>_<reason>.db`. `MAX_BACKUPS=20` rolling window. Reasons in use: `auto`, `manual`, `login` (auto-on-login), `pre_restore`, `pre_hash_migration`, `pre_attachment_migration`, `uploaded`.
- **Filename validator** (`_is_safe_backup_filename`, added 2026-05-05): strict regex `^backup_\d{8}_\d{6}_[a-z_]+\.db$` plus rejects `..`, `/`, `\`. Reused by every backup endpoint that takes a filename param (download, restore, delete) so all of them have one source of truth for what's a legal name.
- **Download** (added 2026-05-05): `GET /api/settings/backup/<filename>` streams the `.db` as `attachment` with `nosniff`. UI: gold "تحميل" button per row in `templates/settings.html`. Works inside the pywebview/WebView2 desktop shell because it's a same-origin navigation, not `window.open` (which the shell blocks).
- **Upload** (added 2026-05-05): `POST /api/settings` with `action=upload_backup` accepts an external `.db` (≤ 50 MB), validates the SQLite magic header (`SQLite format 3\x00`) and runs `PRAGMA integrity_check` on it before saving as `backup_<ts>_uploaded.db`. The upload writes to a hidden `.upload_<uuid>.db` temp name on the same volume first; only renames after validation passes. **Restore stays a separate click** so the existing `pre_restore` safety snapshot still runs.
- The 20-slot rotation can erase manual/pre-restore backups if logins flood the buffer (auto-on-login uses one slot per login). Known limitation, deferred.

## Desktop build (Windows `.exe`)
- `launcher.py` picks a free TCP port (tries 8000–8099, else OS-assigned), starts Flask in a daemon thread on `127.0.0.1`, waits for readiness, then opens a pywebview (WebView2) window.
- `app.py` detects `sys.frozen` to: (a) resolve read-only assets from `sys._MEIPASS`, (b) store the DB + backups under `%APPDATA%\MyPerfumery\database\`, attachments under `%APPDATA%\MyPerfumery\attachments\`, and the random session key as `%APPDATA%\MyPerfumery\secret.key`, (c) disable Flask debug and the reloader. Port/host/debug are controlled by env vars (`MYPERFUMERY_PORT`, `MYPERFUMERY_HOST`, `MYPERFUMERY_DEBUG`).
- **Default bind is `127.0.0.1`** (changed 2026-05-05). Inside Docker (detected via existing `/app` heuristic, same as `_user_data_dir()`) the default flips to `0.0.0.0` so docker-compose port-forward keeps working. `MYPERFUMERY_HOST` env var overrides either way. The frozen `.exe` is unaffected because `launcher.py` already pins `HOST=127.0.0.1`.
- `build.bat` is the local one-click build; `.github/workflows/build-windows.yml` produces the same `.exe` on every main push and attaches it to the rolling `latest` release.
